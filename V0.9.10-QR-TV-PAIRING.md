# TunelyTV v0.9.10 — TV QR-code pairing

## What is implemented

This release is based on **v0.9.9** and adds a QR-based onboarding demo at `/tv` and a responsive phone activation page at `/activate`. It reuses the existing secure TV enrollment, account sign-in, per-user playlist, device entitlement, and revocable sync APIs. The simulator does **not** yet contain a native TV player. Future Android TV / Google TV APKs should reuse this backend with device tokens stored in Android Keystore-backed app storage.

1. The TV preview at `/tv` auto-enrolls a pending device. It displays a **self-hosted QR code**, an eight-character fallback code, and an expiration countdown.
2. Scan the QR with your phone. The QR points to `/activate?code=ABCD-EFGH` on the same TunelyTV server. It **does not contain** a playlist URL, provider credentials, device bearer token, or account password.
3. Sign into your **existing** TunelyTV account on the phone if not already signed in.
4. Choose one of your saved authorized playlists and click **Approve & connect this TV**. Alternatively, choose “set up a playlist later.”
5. The claim endpoint consumes the code, verifies the logged-in account and CSRF token, checks TV slot allowances, and assigns the device to the account. The TV preview polls the existing sync API and shows that it is connected and has received the playlist assignment.

Codes expire in 10 minutes, cannot be used twice, and can be manually regenerated. The device can be revoked under Account → Devices.

### Development / Railway

- Upload the **extracted package contents**, including `site/` and `requirements.txt`, to the existing `ForgeByteGames/TunelyTV` repository. Keep the Railway service, `/app/instance` volume, and original `TUNELY_FERNET_KEY`. Do not upload any `.env`, database or secret key files.
- New dependency: pure-Python `qrcode` library (SVG image generation; no remote QR services or API key).
- New optional variable: **`TUNELY_PAIRING_PUBLIC_URL=https://tunelytv.com`** (or the confirmed HTTPS host serving the same TunelyTV application). Set this when using custom domains, proxy rewrites, or when the QR should always point to the main public website. If omitted, production derives an HTTPS URL from the request host when it is a `tunelytv.com` or `railway.app` hostname. **Do not set this to a domain that is not already serving the `/activate` page.**
- First test **`https://<your-live-railway-host>/tv`** on a separate screen and scan it from a phone; if the custom domain is not live, leave `TUNELY_PAIRING_PUBLIC_URL` unset until it is.
- Existing `/api/device/enroll`, `/api/pairings/claim`, and `/api/device/sync` remain backward compatible with prior TV pairing clients.
- No third-party content, channels, or logos are included. TMDb and external auto-matching remain disabled unless independently authorized.

### Important limitations

- The included `/tv` is a **browser TV pairing and sync preview**, not a finished Android TV / Samsung / LG app; it does not yet play streams. The code path is ready for reuse when the native app is implemented.
- No customer-facing paid plans or payments are enabled by this update. Account permissions and plan restrictions are still applied to paired devices.
- Neither the TV screen nor the QR logs into an account automatically. **Phone confirmation is always required**. A photo of an unclaimed code might be used to initiate linking to the scanning user's account until expiry; approve only a TV you control.
- User-supplied IPTV provider streams may fail for rights, HTTPS, codec or CORS reasons; TV pairing does not bypass those limitations.
- Production operator should configure trusted HTTPS domains and rate-limit API access at their ingress if needed. Pairing codes are rate-limited and expire.

### Testing

Run `python -m pytest -q` from the project root. **65 backend tests passed**, including QR generation, expiry, invalid codes, one-time claiming, login from a separate phone session, playlist assignment, and rights checks. JavaScript syntax was checked with `node --check`. A browser visual check against localhost could not be completed because the test environment blocked localhost access; test layout and camera scanning on real devices before release.
